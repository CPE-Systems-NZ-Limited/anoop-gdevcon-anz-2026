SVN / No SCC: A Ticking Time Bomb

Security & resilience

  • One central server: SVN offline = whole team blocked
  • "Code on a shared drive" has no audit trail
  • No pull-request review gate before release
  • Hard to prove who changed what, when

The AI era

  • AI writes code fast — review has to keep up
  • AI assistants, CI/CD and review tools are Git-native
  • Tamper-evident history: every commit ID depends on all the history before it
  • Optional: sign commits & tags to verify who

Tamper-evident history + reviewed PRs into a protected master

Git commit IDs are hashes over content and parent commits, so rewriting old history changes every later ID: tampering is visible. Author names are free text though; only signed commits/tags verify who made them (GitHub shows "Verified"). Don't claim "cryptographically verified" unless signing is on.

"But I'm a Solo Developer…"

"I'm just one person — why do I need branches?"

  • Time travel — every commit is a save point
  • Zero-fear experiments — git checkout -b experiment; discard a failed idea in a second, no stray .vi copies
  • Off-site backup — push to a remote, sleep at night
  • History is documentation — for clients, audits and handover
  • Your future self is your teammate

on top of WIP]
  • Everyone commits to one line
  • Trunk is never quite releasable
  • Hotfixes ship half-finished features
  • Branching in SVN is heavy, so nobody does it

The same trap in Git: treating master like trunk and pushing raw edits straight to production.

Enter Git Flow for Graphical Developers

master (production) → develop (integration) → feature/* (safe isolation)

feature/* → develop: merge commit · develop → master: reviewed PR + tag vX.Y.Z · hotfix/* → master and develop

No direct commits to master · optional bugfix/* and release/*

CPE standard: features branch from develop, stay narrow and short-lived, merge back with a merge commit and are deleted. develop must stay buildable. master is protected: PR with reviewer approval, no force pushes, every production merge tagged v<major>.<minor>.<patch>. Hotfixes branch from master and merge into both. release/* is optional. (GitHub's default name is main; same role.)

Why GUIs Matter for Graphical Programmers

You don't need a command line to be a DevOps engineer

SourceTree

  • Free (Atlassian)
  • Built-in Git Flow buttons
  • Custom external diff / merge tools

GitKraken

  • Visual commit graph
  • Drag-and-drop merge / rebase
  • Git Flow support built in

TortoiseGit

  • Free, right-click menus in Windows Explorer
  • Familiar for TortoiseSVN users
  • No Git Flow buttons — easy to keep working the SVN way and miss the benefits of Git

Point any of them at LVCompare.exe and LVMerge.exe — VI diffs open in LabVIEW, not as unreadable bytes.

TortoiseGit is fine for developers coming from TortoiseSVN, but it doesn't guide you through Git Flow, so people tend to commit straight to one branch like SVN trunk. If you use it, follow the branching rules deliberately.

Deconstructing the Binary Myth

  • Separate compiled code from source — recompiles stop touching every VI
  • Tell Git which files are binary
  • Ignore generated files
  • Large build outputs and archives go to Git LFS
  • Optional: LFS locking for shared VIs
# .gitattributes
*.vi   binary
*.vit  binary
*.ctl  binary
*.ctt  binary
*.vim  binary

# Git LFS (CPE repo template)
*.exe filter=lfs diff=lfs merge=lfs -text
*.zip filter=lfs diff=lfs merge=lfs -text

# .gitignore
*.aliases
*.lvlps
builds/

Scaling for Systems Integrators

Lessons from CPE Systems NZ · SVN → Azure DevOps Git for a large industrial test-equipment customer

50 repos

23 hardware · 26 software · 1 shared library, migrated in January 2026

4 super-repos

Git submodules group components into deployable test systems

History kept

SVN authors mapped to Git identities, so history stays traceable

One template for every repo · access limited per customer project · pilot first, then batch · protected master

Customer anonymised on purpose (public repo). Dozens of customer repos: same template (.gitignore, .gitattributes with LFS, folder layout) everywhere. Repository access is limited per project, and external collaborators get guest access. Phased rollout: one simple repo, then a complex one, then a super-repo, then batch. Author mapping with a default fallback, iterated over several rounds. Submodules use relative URLs; every super-repo has a README.

  • Protect master: every change through a reviewed PR
  • Branch every change from develop; tag releases vX.Y.Z
