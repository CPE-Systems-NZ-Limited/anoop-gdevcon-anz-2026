SVN / No SCC: A Time Bomb

Security & resilience

  • One central server = one point of failure
  • "Code on a shared drive" has no audit trail
  • No pull-request review gate before release
  • Hard to prove who changed what, when

The AI era

  • AI assistants, CI/CD and code review tooling are Git-native
  • GitHub, GitLab, Azure DevOps all speak Git
  • Without history, AI-assisted changes are unreviewable
  • Hiring: new engineers expect Git

"But I'm a Solo Developer…"

  • Undo with confidence — every commit is a save point
  • Experiment freely — branches cost nothing
  • Off-site backup — push to a remote, sleep at night
  • History is documentation — for clients, audits and handover
  • Your future self is your teammate

  merge hotfix/1.1.1

feature/* → develop: merge commit · develop → main: reviewed PR + tag vX.Y.Z · hotfix/* → main and develop

No direct commits to main · optional bugfix/* and release/* · at CPE the production branch is master

CPE standard: features branch from develop, stay narrow and short-lived, merge back with a merge commit and are deleted. develop must stay buildable. Production (master in our Azure DevOps repos, main on GitHub) is protected: PR with reviewer approval, no force pushes, every production merge tagged v<major>.<minor>.<patch>. Hotfixes branch from production and merge into both. release/* is optional.

Graphical Git Clients

SourceTree

  • Free (Atlassian)
  • Built-in Git Flow buttons
  • Custom external diff / merge tools

GitKraken

  • Visual commit graph
  • Drag-and-drop merge / rebase
  • Git Flow support built in

TortoiseGit

  • Free, right-click menus in Windows Explorer
  • Familiar for TortoiseSVN users
  • Configurable diff / merge tools

Point any of them at LVCompare.exe and LVMerge.exe — VI diffs open in LabVIEW, not as unreadable bytes.

Deconstructing the Binary Myth

  • Separate compiled code from source — recompiles stop touching every VI
  • Tell Git which files are binary
  • Ignore generated files
  • Large build outputs and archives go to Git LFS
  • Optional: LFS locking for shared VIs
# .gitattributes
*.vi   binary
*.vit  binary
*.ctl  binary
*.ctt  binary
*.vim  binary

# Git LFS (CPE repo template)
*.exe filter=lfs diff=lfs merge=lfs -text
*.zip filter=lfs diff=lfs merge=lfs -text

# .gitignore
*.aliases
*.lvlps
builds/

Lessons from CPE Systems NZ

SVN → Azure DevOps Git for a large industrial test-equipment customer

50 repos

23 hardware · 26 software · 1 shared library, migrated in January 2026

4 super-repos

Git submodules group components into deployable test systems

History kept

SVN authors mapped to Git identities, so history stays traceable

Pilot one repo first, then batch · protected master: every change through a reviewed PR

Customer anonymised on purpose (public repo). Phased rollout: one simple repo, then a complex one, then a super-repo, then batch. Author mapping with a default fallback for unknown users, iterated over several rounds. Software repos: PCBA firmware, TestStand sequences, rack software, deployment code. Submodules use relative URLs; every super-repo has a README explaining its structure. Team guides cover Git for SVN users plus SourceTree, TortoiseGit and GitKraken.
